# Cуществующие и потенциальные проблемные места:

- всего один инстансанс у каждого приложение
- инстансы базы данных работают и на запись и на чтение
- ручной деплой в релиз и продашкн, риски ошибок
- нет статусов при заказе через MES API
- отсутствует кеширование при получении списка заказов
- нет статуса [заказ получен для расчета стоимости] MES
- статус [заказ завершен] может быть закрыт вручную, нет подтверждения от клиента
- нет мониторинга заказов, отслеживания их статусов и выдачи алертов в случае "зависания" 
  заказа в каком-то статусе более установленного для него срока

# Целевая архитектура через полгода

Микросервисная архитектура, использование балансировщика нагрузки, автоматическое масштабирование,
репликацию и кеширование, паттерна CQRS, back pressure и circuit breaker

# Инициативы, которые необходимы для устранения нежелательных ситуаций:

1. Раз все инстансы крутятся в облаке, то необходимо в первую очередь настроить
балансировщик нагрузки и автоматическое масштабирование.
Для баз данных настроить репликацию и кеширование + реализовать CQRS.

2. Раз производственные мощности позволяют справиться с заказами, и клиенты
жалуются что заказы долго делаются и не доходят до клиентов, значит проблема точно есть
в прохождении событий через RabbitMQ. Каждая из систем может не знать что предыдущая отправила
событие, которое ей необходимо обработать, т.к. либо сама не справилась с входящими сообщениями,
либо очередь сообщений перегружена. Для очереди сообщений настроить back pressure.

3. Для решения проблемы с долгой загрузкой MES помимо мер в п.1 добавить circuit breaker 

Остальные инициативы:
- разделение на микросервисы
- внедрить автоматическое тестирование
- настроить CI/CD
- использовать канареечные релизы
